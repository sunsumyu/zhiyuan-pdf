# naming-audit

批量扫描 Rust 项目函数命名问题的 skill。调用本 skill 前先读取 `references/scan_rules.md` 了解扫描规则。

## 工作流

### 1. 确认扫描范围

先问用户想扫描哪个范围：
- **全项目扫描**：项目根路径下所有 `.rs` 文件
- **模块扫描**：指定目录（如 `crates/pdf-viewer-core/src/edit/`）
- **文件扫描**：单个文件

### 2. 获取候选函数列表

使用 Bash 获取目标范围内所有 `pub fn` 和 `pub(crate) fn`：

```bash
cd <project-root>
grep -rn "^pub fn\|^pub async fn\|^pub(crate) fn\|^pub(super) fn" <target-path> --include="*.rs"
```

### 3. 逐函数扫描

对每个函数执行扫描（Chain of Thought 推理链）：

#### 3.1 读取函数定义

用 Read 读取文件，获取完整的函数签名、doc comments、参数名。

#### 3.2 推理链（CoT）

对函数执行以下推理步骤：

**Step 1 — 功能摘要**
- 函数做什么？（用一句话概括）
- 是纯函数还是有副作用？
- 返回什么？

**Step 2 — 术语一致性检查**
- 参数名是否和类型名一致？
  - 例：类型 `ParagraphEditContext` 但参数名 `session` → ❌ 术语漂移
- 同模块内是否用不同词指代同一概念？

**Step 3 — 模块重复检查**
- 函数名是否包含模块名已提供的上下文？
  - 例：`edit_target.rs` 中 `collect_edit_targets_from_session` → ❌ 包含 `edit_target`
  - 例：`paragraph_scene.rs` 中 `build_paragraph_editor_scene` → ❌ 包含 `paragraph_scene`

**Step 4 — 动词精准性检查**
- 动词前缀是否匹配实际语义？
  - `build_` → 是否在做复杂组装？
  - `resolve_` → 是否在从多个候选中选择？
  - `collect_` → 是否在遍历集合并收集？
  - `find_` → 是否在搜索/遍历？
  - `get_` → 是否只是简单字段访问？（如果是，去掉 get_）
  - `execute_` → 是否太重了？

**Step 5 — 开源框架对比**

对照 `references/scan_rules.md` 中的"开源命名基准"，判断该函数是否符合业界最佳实践：

| 基准框架 | 检查问题 |
|---------|---------|
| **serde** | 同一类操作是否使用统一前缀？ |
| **tokio** | 模块路径已提供的上下文，函数名是否重复了？ |
| **clap** | `get_` 前缀是否必要？ |
| **rustc** | 返回 bool 的函数是否使用 `is_`/`has_`？ |
| **anyhow** | 是否可以更短？ |
| **std** | 转换方法是否遵循 `as_`/`to_`/`into_` 契约？ |

**Step 6 — 综合判定**

根据 Step 2-5 的结果，判定：
- 🟢 **无需改动**：命名符合所有原则
- 🟡 **建议改进**：有小问题但不影响使用
- 🔴 **需要重命名**：命名与功能严重不匹配

### 4. 输出格式

对每个有问题的函数输出：

```
────────────────────────────────────────────────────────────────
🔴 {函数名}  ({文件路径}:{行号})
────────────────────────────────────────────────────────────────

【当前命名】
{完整签名}

【功能摘要】
{一句话概括}

【问题诊断】
| 检查项 | 结果 | 说明 |
|--------|------|------|
| 术语一致性 | ❌ | 参数名 "session" 与类型 "ParagraphEditContext" 不一致 |
| 模块重复 | ❌ | 函数名包含 "edit_target"，模块名已是 edit_target.rs |
| 动词精准 | ❌ | "collect" 暗示遍历收集，实际是做构建/转换 |
| 开源对比 | ❌ | tokio 风格：模块已提供上下文，应缩短为 build_targets |

【建议重命名】
→ {新名称}

【理由】
{CoT 推理链的完整理由}

【调用影响】
{估算有多少调用点需要更新}
```

## 注意事项

- **只读扫描**，不修改任何文件。
- 扫描结果直接以 Markdown 消息发送给用户。
- 如果扫描范围很大（>100 个函数），先扫描高频模块（如 `edit/` 模块），再按需扩展。
- 引用代码使用精确路径 + 行号格式。
